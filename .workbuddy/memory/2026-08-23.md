# 2026-08-23 — Word card UX pass (mvp/feat/word-card)

## What landed

- `src/ui/word-card.ts`
    - **Copy button** after the speak button (`dial-word-card-copy`).
      Always rendered (clipboard is browser-native), so it shows even when no
      speech engine is available. `navigator.clipboard.writeText(word)` then
      `new Notice('Copied "<word>"')`. Failures (insecure context, denied
      permission) log to console + show a single failure notice (no spam).
    - **Document-level scroll/touchmove dismissal.** The previous listener in
      `subtitle-panel.ts:298` only caught scrolls on the inner
      `.dial-subtitle-list`. Mobile users (Obsidian iOS/Android) often scroll
      the panel viewport or the surrounding leaf, which never bubbled to that
      listener. Now `attachDismissHandler()` (mobile) wires `click`, `scroll`,
      and `touchmove` to `document` with **capture phase** so the card hides on
      any gesture that takes focus away — swipe, wheel, programmatic scroll
      (`setCurrentSubtitle`'s `scrollIntoView`). Desktop path gets just the
      `scroll` capture listener (`handleDocumentScroll`) so hover continues
      to work as today. Card-internal scrolls/touchmoves are excluded via
      `cardEl?.contains(target)` so user interaction inside the card body
      never dismisses it.
    - `hide()` now also detaches the desktop `removeScrollListener` so closed
      cards don't leak listeners on the next open.

- `styles.css`
    - Combined `.dial-word-card-speak` and `.dial-word-card-copy` into one
      rule pair so copy visually matches speak (transparent, square hover
      background, muted color → normal).

- `src/modules/translation/translation-chain.ts` - Dropped the per-engine `new Notice(...)` that surfaced
  `Tencent Cloud translation fails: tencent translate returned no
translation` whenever a cloud translate API came back empty. A
  benign "no translation" isn't actionable and crowded out useful
  signals. The chain still records the real outcome in
  `_lib/logs/YYYY-MM.jsonl` (kind=translation, source=none, ok=false),
  which is the right surface for investigating. Failed configs still
  log to console.

## Cache naming — reminder for self

- Audio cache path: `_lib/cache/audio/YYYY-MM/{hash}.mp3`
- Hash input: FNV-1a over `${lang}:${word}` (e.g. `en-US:have`). Output is
  8-char lowercase hex. Computed in `audioHash` (src/modules/word-cache/audio-cache.ts:15).
- Files persist across engine reorder; the cache doesn't carry the engine
  id, so changing the speech priority loses no data but also can't tell
  you later which engine wrote which file.
- For verification: re-run the FNV loop in `node -e ...` and compare to
  the on-disk name; or read the JSONL log under `_lib/logs/YYYY-MM.jsonl`
  (look for `kind:"speech"`, `engine:"<provider>"`, `source:"engine"`
  vs `source:"current"` / `"promoted"`).

## Follow-up fix — Tencent TMT response field name (same day)

Symptom: speech log shows `engine:"tencent"`, `ok:true`, but translation
log shows `engine:"cache-miss"`, `source:"none"`, `ok:false` for the same
word. So Tencent TTS works, Tencent TMT apparently also returns 200 OK
(no `Error.Code`), yet the chain reports "no translation returned".

Root cause: `tencent-translate-provider.ts` read `Response.TranslatedText`,
but TMT `TextTranslate` actually returns `Response.TargetText` (per the
official Tencent Cloud TMT API doc — `TargetText string 翻译后的文本`,
plus `Source`, `Target`, `RequestId`). `TranslatedText` does not exist on
this action, so it always came back `undefined` and the provider threw
every single time — masking a real successful call as a soft failure.
The previous commit `225c8c4` fixed the TC3 region header, which is why
the request now returns 200 OK instead of `MissingParameter: Region`;
the field-name bug then became the only remaining blocker.

Fix: read `Response.TargetText` instead. Updated the matching test mock
in `tencent-translate-provider.test.ts` (was asserting on the wrong
field name too, so the bug was invisible to the suite).

Lesson: when a cloud provider returns 200 OK with no `Error.Code` but the
integration logs "no translation returned", double-check the response
field name against the actual API doc — not just the local mock. The mock
will happily return whatever the test author wrote, even if the field
doesn't exist in production.
